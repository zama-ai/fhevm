# `@fhevm/hardhat-plugin` — Hardhat v2

Skeleton. The build, the packaging and the resolution guard are in place; the plugin itself is empty.

## Layout

The same harness/payload split the `host-contracts-cleartext` generations use:

|                            |                                                                                           |
| -------------------------- | ----------------------------------------------------------------------------------------- |
| `package.json`             | HARNESS. Private, never published. Every devDependency, every script, all tooling config. |
| `pkg/`                     | PAYLOAD. What gets published, and nothing else.                                           |
| `pkg/package.json`         | The published manifest — no scripts, no devDependencies.                                  |
| `pkg/src/`                 | TypeScript sources. Shipped as well as compiled, so a consumer can read them.             |
| `pkg/_cjs/`, `pkg/_types/` | Build output. Gitignored, regenerated by `npm run build`.                                 |
| `internal/`                | Harness-only tooling. Never published.                                                    |
| `test/`                    | Harness tests. Never published.                                                           |

`.npmignore` cannot produce that split: it filters files, not manifest fields. Two manifests can.

## CJS only

`pkg/package.json` declares `type: commonjs` and ships a single build. Hardhat v2 loads plugins with
`require`, so an `import` condition would add a resolution path nothing exercises.

The harness above it declares `type: module`. That is the mechanism, not an inconsistency — the nearest
`package.json` decides a file's module format, so `internal/` and `test/` are ESM like every other harness
here while everything under `pkg/` is CommonJS.

`build:cjs` writes `pkg/_cjs/package.json` containing `{"type":"commonjs"}` after `tsc`. Without that stub
Node applies the harness's `type: module` to the emitted `.js` and a consumer gets `ERR_REQUIRE_ESM`.

## node10

Hardhat v2 consumers typecheck with `module: CommonJS` + `moduleResolution: node10`, which **ignores the
`exports` map completely**. `main` and `types` are the entire contract.

That failure is silent: with a wrong `types`, node10 falls back to directory resolution, lands on
`pkg/src/index.ts`, and compiles our TypeScript with the consumer's settings. Nothing errors.

So `test/node10-cjs-resolution.test.ts` asserts the resolved **path**, not that it compiled — it builds a
throwaway node10 consumer and reads `tsc --traceResolution` to confirm it landed on `_types/index.d.ts`
and _not_ on `pkg/src/index.ts`. Both directions are injection-tested.

The build configs compile under `moduleResolution: node10` for the same reason, with
`ignoreDeprecations: "6.0"` because TypeScript 6 deprecates it and 7 removes it.

## Commands

```sh
npm run build          # clean, prettier, lint, cjs, types, publint + attw
npm test               # the node10 resolution guard (run after a build)
npm run build:cjs      # tsc -> pkg/_cjs  + the {"type":"commonjs"} stub
npm run build:types    # tsc -> pkg/_types
npm run test:publint   # publint --strict ./pkg && attw --pack ./pkg
```

## Before publishing

- **`version` is `0.0.0`.** Deliberate: the skeleton implements nothing, and `0.0.0` cannot be mistaken
  for a release. Set it when there is something to release.
- **`dependencies` is absent.** The model plugin declares `debug`, `picocolors`, `dotenv`, `resolve` and
  `@fhevm/host-contracts-cleartext`; none is added here until code imports it, so the manifest never
  claims a dependency the payload does not have.
- **`peerDependencies` is `hardhat: ^2.0.0` only.** The model also peers `@fhevm/sdk`, `@fhevm/solidity`,
  `@nomicfoundation/hardhat-ethers`, `ethers` and `encrypted-types`. Those are contracts with the
  consumer, so they belong here as the plugin starts using them — not before.
